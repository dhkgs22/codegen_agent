# 项目总结：多智能体代码助手（项目 I）

## 一、项目背景

2026 年暑期，我参加了以"AI Agent 成长实践"为主题的暑期实践项目。在为期数周的学习中，我系统掌握了 AI 命令行工具的使用、Agent 与 Skill 的概念、MCP 插件机制，以及循环工程（Loop Engineering）、上下文工程（Context Engineering）、子智能体（Sub-Agent）与多智能体（Multi-Agent）等进阶方法。

在第四周的选题阶段，我选择了计算机方向的**项目 I——多智能体代码助手**。选择这个项目的原因有三点：第一，它是最具综合性的 CS 项目，需要同时运用 FastAPI、WebSocket/SSE 流式传输、多智能体编排和 CI/CD 等多项技术；第二，它的核心思路——"用 AI 写代码、用 AI 修代码、用 AI 写文档"——和我在课程中学到的 Agent 工程方法高度契合；第三，它具备完整的工程化闭环，从需求到测试到发布，能在答辩中充分展示我的综合能力。

## 二、需求分析与设计

在日常软件开发中，"写代码、运行代码、修 Bug、写文档"是四个最耗时也最机械的环节。本项目的目标，就是构建一个多智能体系统，让用户仅需用自然语言描述需求，系统即可自动完成上述全部环节。

系统设计为四个核心模块：

1. **Coordinator（总控编排器）**：解析用户任务，负责调度各个 Agent，并维护贯穿全程的事件流。它是整个系统的大脑。
2. **Code Agent**：接收自然语言任务描述，调用大语言模型生成一份完整、可直接运行的 Python 程序。
3. **Debug Agent**：在隔离的沙箱环境中运行生成的代码。若运行失败，它会把报错信息反馈给大语言模型，自动分析原因并生成修复后的代码，循环往复，直至运行通过或达到轮次上限。
4. **Doc Agent**：在程序运行通过后，自动生成包含功能说明、使用方法和示例输出的 README 文档。

系统对外提供三种使用方式：命令行（CLI）、基于 FastAPI 的 REST 与 SSE 流式接口、以及基于 Streamlit 的可视化 Web 界面。事件流通过事件总线（EventBus）广播，使得 CLI、SSE 端点和 Web 界面能够实时展示每个 Agent 的工作过程。

## 三、技术实现

### 1. LLM 抽象层

考虑到 DeepSeek API 与 Anthropic Claude API 都遵循 OpenAI 兼容的接口规范，我设计了统一的 LLM 抽象层（`app/llm/client.py`），定义了 `chat` 统一接口。`DeepSeekClient` 实现了真实的 API 调用，支持流式输出回调；`FakeClient` 用于测试场景，返回预设内容，使测试不消耗任何真实 token。这一设计使系统可以随时切换到其他大模型提供商。

### 2. 沙箱执行环境

为确保 LLM 生成的代码在隔离环境中安全运行，我实现了沙箱模块（`app/sandbox/runner.py`）。它使用 `subprocess` 在独立的临时目录中执行代码，通过 `timeout` 参数强制限制运行时间，防止死循环拖垮系统；同时捕获标准输出、标准错误和退出码，为 Debug Agent 提供结构化的报错信息。

### 3. 修复循环机制

Debug Agent 的核心是一个"运行-诊断-修复"的迭代循环。每轮循环中，系统在沙箱中运行代码；若失败，将退出码、标准输出和报错堆栈一并反馈给大语言模型，由模型生成修复后的完整代码；随后进入下一轮运行。轮次上限可配置（默认 3 次），既保证修复成功率，又避免无限循环。

### 4. 事件流与实时反馈

我设计了统一的事件模型（`app/events.py`），包括 start、code、run、fix、doc、done、fail 等事件类型。Coordinator 和各 Agent 通过事件总线发布事件，前端（Streamlit）和后端（SSE）订阅并实时渲染。这使得整个多智能体的协作过程完全透明、可视化。

### 5. 工程化与 CI/CD

项目采用 pytest 编写了 15 个测试用例，覆盖沙箱执行、代码提取、修复循环、失败终止、CLI 输出和 API 端点等关键路径。配置了 GitHub Actions 持续集成，每次推送自动安装依赖并运行全部测试。项目发布到 GitHub，附带 MIT License、贡献指南和 v1.0.0 版本 Release。

## 四、开发过程

整个项目按照实践任务书安排的节奏推进。前两周完成了基础工具链的学习与配置，包括命令行工具、Agent 与 Skill 的掌握，以及循环工程、上下文工程等进阶概念；同时提前配置好 DeepSeek API 密钥和 Python 虚拟环境。

第四周进行项目选型与预研，产出了包含架构设计、技术选型和风险评估的预研文档 plan.md。第五周集中开发 MVP，遵循"先跑通单条链路、再扩展"的原则：先实现 Coordinator 与三个 Agent 的核心逻辑和沙箱执行，让命令行方式端到端跑通；随后补齐 FastAPI 后端与 SSE 流式接口；最后用 Streamlit 搭建可视化界面，并统一接入事件流。第六周完善工程质量，编写 pytest 测试、配置 GitHub Actions 持续集成、补充 README 与贡献指南，并发布 v1.0.0 版本。

开发过程中遇到了几个值得记录的问题。其一，Windows 平台的终端默认使用 GBK 编码，无法输出中文和 emoji 字符，导致命令行程序在打印结果时直接崩溃，通过重配置标准输出编码为 UTF-8 解决。其二，在沙箱中直接执行 .py 文件会触发系统错误，经过排查发现需要显式调用 Python 解释器来运行脚本，而不是把脚本文件当作可执行程序直接执行。其三，生成代码若读取命令行参数而没有默认值，在沙箱无参运行时会产生索引越界错误，因此通过修改提示词要求模型为所有输入参数提供默认值。这些问题的排查与解决，显著提升了我的调试能力。

## 五、项目成果

1. **功能完整**：系统实现了从自然语言到可运行程序的完整闭环，支持自动写代码、自动运行、自动修复（至多 N 轮）、自动生成文档。
2. **质量可靠**：15 个 pytest 测试全部通过，GitHub Actions CI 全绿；使用 Fake LLM 进行测试，不消耗 token。
3. **真实可用**：使用真实 DeepSeek API 端到端验证通过——输入"写一个程序输出前 n 个偶数"，系统生成代码、沙箱运行成功、自动生成 README，全程约 7.5 秒。
4. **三种入口**：CLI、REST/SSE API、Streamlit Web 界面全部实测可用。
5. **工程规范**：MIT License、CONTRIBUTING 贡献指南、GitHub Release v1.0.0、规范的 commit 记录。

## 六、收获与不足

**收获**：通过本项目，我深入理解了多智能体系统的核心思想——通过职责单一的子智能体分工协作，完成单个模型难以稳健处理的任务；掌握了事件驱动的架构设计、沙箱隔离执行、LLM 接口抽象和 CI/CD 自动化等工程方法；也体会到了"让 AI 辅助开发"的真实生产力提升。

**不足与展望**：当前版本仅支持单文件 Python 项目，尚未支持多文件工程和第三方依赖安装；修复效果在一定程度上依赖大语言模型的生成质量；尚未对修复成功率进行系统的 Benchmark 统计。后续计划增加多文件与依赖支持、加入自动生成测试用例的 Agent，以及建立成功率、耗时的量化评估体系。

## 七、结语

本次暑期实践让我从零构建了一个完整的多智能体应用，深刻体会了 AI Agent 从理论到工程的落地过程。这不仅是技术的提升，更是思维方式的一次升级——学会把复杂任务拆解为可协作的智能体单元，用工程化的方法保证质量与可交付性。回顾整个暑假，从第一周安装配置工具链，到写出第一个可运行的命令行程序，再到最终的 Web 界面、CI 自动化与版本发布，每一步都建立在持续学习与反复调试之上。我也认识到，AI 辅助开发并不是"让机器替人写代码"那么简单，真正有价值的是人如何定义清晰的任务边界、设计合理的分工协作机制，并依靠工程手段保证产出可靠。这段经历让我对 AI 工程化应用建立了更完整的认知，也让我更有信心在未来接触更复杂的智能体系统。感谢老师的指导与这次宝贵的实践机会，这将是我专业成长路上非常重要的一段积累。
